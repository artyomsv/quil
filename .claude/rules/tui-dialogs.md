# TUI Dialogs

Extracted verbatim from `.claude/CLAUDE.md`. Loaded only when the files above are in play.

## Dialog system

### Dialog system

`internal/tui/dialog.go` — modal dialogs with `dialogScreen` iota (`dialogAbout`, `dialogSettings`, `dialogShortcuts`, `dialogConfirm`, `dialogCreatePane`, `dialogCreatePaneSetup`, `dialogPluginError`, `dialogInstanceForm`, `dialogPlugins`, `dialogTOMLEditor`, `dialogLogViewer`, `dialogDisclaimer`, `dialogPluginMigration`, `dialogProcesses`, `dialogGitRepoPick`, `dialogWhatsNew`). F1 opens About dialog with 10 items: Settings, Shortcuts, Plugins, Processes, View client log, View daemon log, View MCP logs, Update (`aboutUpdateIndex`, dynamic label), What's New (`aboutWhatsNewIndex`, opens the post-upgrade highlights for the newest release), Stop daemon (the last is a destructive action at `aboutStopDaemonIndex`, routed through the shutdown confirm). Ctrl+N opens typed pane creation dialog (category → plugin → instance → setup → split). `dialogCreatePaneSetup` (between plugin/instance and split) renders the directory browser + runtime toggle checkboxes for plugins that opt in via `prompts_cwd` / `[[command.toggles]]`. CWD browser pre-fills from `lastSelectedCWD` (remembers previous choice within the TUI session), then active pane OSC 7 CWD, then home dir; candidates are tried in order — stale directories are skipped and the memory is cleared.

**The dialog serves TWO targets** (`Model.createPaneTarget`): `paneTargetSplit` (Ctrl+N, into the active tab) and `paneTargetNewTab` (Ctrl+T, as a new tab's first pane). Steps 0–2 plus the setup dialog are identical; only the LAST step differs, and `advanceFromPluginChoice` is the single place that decides — a split still asks H/V/Replace, a new tab has no pane to be relative to so those three rows cannot mean anything and it submits instead. It replaced FOUR scattered `createPaneStep = 3` assignments that all had to agree. `handleCreatePaneSplit` branches for the new-tab case AFTER its teardown block and BEFORE everything else: `m.dialogCursor` is read below it to pick the split direction and holds whatever the last list left there (the placement step never ran), the active-tab/active-pane requirements describe a pane to split FROM (skipping them is also what keeps Ctrl+T working in the pre-first-broadcast window, when there is no tab yet), and `pendingSplit`/`worktreeCreates`/`worktreeReplaced`/the give-up tick are all keyed by a tab id that does not exist until the daemon answers — nothing is detached and no leaf is reserved, so there is nothing to unwind and nothing to time out.

**`createPaneTarget` is reset in `openCreatePaneDialogFor`, never on a close path**, and it is a PARAMETER rather than a field somebody sets afterwards. Three exits never reach the teardown: the step-0 Esc, the instance-delete detour into `dialogConfirm`, and `handleCreatePaneSplit`'s early refusals. A target surviving one of those makes the next plain Ctrl+N create a TAB instead of a split — the fourth recurrence of the stale-dialog-state class this file documents three of.

**`Model.createPaneDest` pins the destination at OPEN, and the submit uses `sendForDestStrict`.** The old `createTab` sent UNSTAMPED (`m.client.Send`), which was safe only because the keypress and the send were the same instant; a dialog sits open for as long as the user takes, and MCP `set_active_pane` moves the active project with no keyboard involved. Every value in the form describes the open-time daemon's disk — the browse and git-discovery listings were answered by it — so submitting against a different one hands, at worst, a `WorktreeSpec.RepoRoot` describing machine A to machine B's `git worktree add`. Strict because `Router.Send` drops an unroutable message and returns nil, so the loose form cannot report a tab that was never created; the failure arrives as `createTabFailedMsg`, whose arm must NOT re-arm `listenForMessages` (it is a send result, not an IPC response).

**Esc creates the terminal tab only on the step-0 (dialog-CLOSING) branch.** Esc deeper in is back-navigation and always has been; making every Esc create a tab would remove the only way back a step and make one key mean two things depending on how far in you are. `setupDiscoveryBase` follows the same target split — a split discovers from the active pane's OSC 7 CWD (that pane IS the context), a new tab from the active project's `RootDir`, which is what the daemon's `projectCWD` roots it at anyway. The reachability refusal moved from the keypress into `handleNewTab` (dialog-open time), carrying BOTH carve-outs with it — a nil `m.cur()` and `onlyOfflineProjects()` are the pre-first-broadcast window, not an unreachable host.

**Recent-locations quick pick**: for `prompts_cwd` plugins with no git-discovered repos, `enterSetupOrSplit` offers the last 5 committed CWDs (`Model.recentCWDs`, persisted TUI-owned to `config.RecentCWDsPath()` = `recent-cwds.json` via `LoadRecentCWDs`/`SaveRecentCWDs`, pushed in `handleCreatePaneSplit` via pure `pushRecentCWD` — dedup, cap `recentCWDMax=5`, Windows-case-insensitive) as `Model.recentCandidates`, filtered by `existingDirs` (drops deleted folders). This reuses the git repo pick-list UI: `activeCWDPick()` returns `(repoCandidates` else `recentCandidates`, isRecent)`; render + `handleSetupPickKey` (renamed from `handleSetupRepoKey`) are source-agnostic. Enter on a row submits; "Browse…" clears both pick lists and drops to `initSetupBrowser()`. Git discovery keeps priority.

**Committed-value marker (`setupRowIdleMark`)**: the cursor caret (`"  > "` + `dialogSelected`) is drawn only on the FOCUSED field's cursor row, so the dialog used to show nothing at all for the chosen directory in two states — the field blurred (Tab moved on), and the field focused with the cursor parked on the trailing "Browse…" row, which `syncSelection` deliberately never commits. Both now mark the committed row with `setupRowIdleMark` (`"  ▸ "`) + bold `dialogSelectedIdle`. Guards: the mark is exactly `setupRowIndent` cells so `leftTruncPath`'s budget is unchanged (`TestSetupRowIdleMark_MatchesRowIndent` — U+25B8 is East-Asian-Ambiguous, so the test pins what lipgloss MEASURES, same exposure as the pre-existing `"● "` kube current-context marker); the glyph is `▸` not `•` because the kube current context renders `"● "` and `"  • ● prod"` puts two near-identical dots side by side.

**Bold is never the load-bearing signal** — `dialogValStyle` and `dialogNormal` are the same declaration and `dialogSelectedIdle` differs from both by SGR `1` alone, so a terminal that drops bold sees only the mark; that is why browser mode's standalone path line takes the mark too (not just the bold) and why the tests assert on ANSI-STRIPPED output keyed to the prefix.

**The CWD case is not `!focused`-gated** (case order alone lets the caret win when the cursor is already on the committed row) and matches on `cwdBrowseDir` — the value `submitSetupDialog` reads — NOT `cwdBrowseCursor`, which is exactly what makes the Browse… state work; in pick mode `cwdBrowseDir` is only ever assigned by copying an element out of the same slice being rendered, so `==` is exact by construction and never reaches `pathEqual`'s Windows case-folding (and duplicate rows are unreachable: `gitdiscover.Candidates` dedupes via `seen` and is structurally incapable of them, `recentCandidates` comes from `pushRecentCWD`'s `pathEqual` dedupe).

**The kube case IS `!focused`-gated** even though case order makes it redundant — `renderRow` closes over `focused`, so without the explicit guard a future reorder would silently mark the focused row with nothing failing (`TestRenderSetup_KubeFocused_NoIdleMark` is the reorder canary); kube needs no value indirection because row 0 ("Default context") is itself a real choice, so `kubeCursor` IS the committed value. Collapsing the field to a one-line summary (the `renderSetupSessionField` pattern) is deliberately NOT used here — that works only because the session picker is the LAST field, and collapsing the FIRST field moves every row below it on each Tab (`TestRenderSetup_PickFocusChange_HeightStable` pins the invariant). Instance form rendered from plugin `FormFields`. TOML editor renders full-screen (bypasses dialog box). `dialogLogViewer` reuses the same full-screen `TextEditor` but with `ReadOnly=true` and `HighlightPlain` so users can scroll/copy log content without overwriting it. `Alt+Up`/`Alt+Down` jump the cursor by `cfg.UI.LogViewerPageLines` lines (default 40). `openLogViewer(label, path)` and `openMCPLogsViewer()` build the read-only buffer; `readLogTail` caps each file at 256 KB and trims to a clean line boundary. Confirm dialog used for pane/tab close (Ctrl+W / Alt+W) and instance deletion

### Beta disclaimer

`dialogDisclaimer` shown on startup when `ui.show_disclaimer = true` (default). Random tip from `disclaimerTips` slice. Two buttons: OK (close) and "Don't show again" (sets `cfg.UI.ShowDisclaimer = false`, persisted via `config.Save()` on TUI exit). `configChanged` flag on Model signals `main.go` to write config

## Command palette

### Command palette (M11)

`command_palette` (default `alt+shift+p` ONLY — `ctrl+shift+p` is intercepted by many terminals' own palette (Windows Terminal, VS Code) before Quil sees it, so it is opt-in) opens a modal, centered, keyboard-first fuzzy-find launcher (`internal/tui/palette.go`) — a `dialogScreen` (`dialogCommandPalette`), NOT a compositor overlay like the context menu (it needs no mouse anchoring and inherits input routing + `lipgloss.Place` centering from the dialog system). State is `Model.palette paletteState` (query/cursor/commands/filtered; zero value = empty, `m.dialog` is the sole open/closed authority — no `open` bool, mirrors `ctxMenu`). `buildPaletteCommands` rebuilds the registry on every open, GROUPED under dim section headers (`paletteCommand.header`) in fixed order, NAVIGATION FIRST — **Go to pane** (one row per pane across all tabs, labelled `<tab>.<pane> · <type>[· name]` + short CWD detail so same-name/same-dir panes are distinct), **Tabs** (switch-to first, then new/close/rename/cycle-color), **Pane** (actions on the active pane), **System** (settings/plugins/memory/about/logs/redraw). Per-active-pane gates (`Input history` needs `record_history`, `Open lazygit` needs the binary) and toggle labels (mute/eager) reflect current state. Fuzzy match is a hand-rolled greedy subsequence scorer (`fuzzyScore`/`commandScore`) — case-insensitive, rewards consecutive runs + start/separator boundaries. `filterPalette` has TWO modes: empty query = browse (all rows incl. headers, registry order); non-empty = search (headers dropped, matches stable-sorted by score). `paletteCommand.selectable()` (= `!header && enabled`) gates cursor movement (`firstSelectable`/`nextSelectable` skip headers + disabled rows, no wrap) and Enter. `executePaletteCommand` is a THIRD dispatcher (alongside the key switch and context menu) that routes each `paletteAction` into the SAME existing handler methods — pane-scoped actions act on the active pane; `palActGoToPane`/`palActSwitchTab` change the active tab/pane (go-to clears the old tab's active-pane `.Active` flag BEFORE `switchTab` moves `m.activeTab` — load-bearing ordering). Reuses four handlers extracted from `handleKey` for this: `openCloseTabConfirm`/`beginTabRename`/`openCreatePaneDialog`/`forceRedraw`. Input: `msg.Text` typing gated by `isPrintableText` (drops control chars incl. tab); paste (`tea.PasteMsg`) folded into the query via `sanitizePaletteQuery` (dedicated `dialogCommandPalette` branch — else it would leak into the hidden pane's PTY); `ctrl+p`/`ctrl+n` alias up/down. No-op in notes mode (explicit `openCommandPalette` guard — `notesKeyExempt` governs only the editor-focused path). `renderCommandPalette` returns box CONTENT (renderDialog sets `width = paletteWidth`, clamps to `m.width-2`); `paletteInnerWidth` is `boxW-6` (2 border + 4 padding — lipgloss draws the border INSIDE `.Width`, so a full-width row of `boxW-4` soft-wraps its right-aligned shortcut onto the next line), and rows/headers/hints all clamp via cell-aware `truncateToWidth`/`lastCellsToWidth` so wide-glyph names and long queries never wrap the border.

**Content search is UNIFIED into the palette** — there is NO `/` prefix or separate mode. Whenever the query is non-empty, `afterPaletteQueryChange` refilters the commands AND fires a debounced content search over every pane's buffered scrollback (all tabs, incl. background + muted), via IPC pair `MsgPaneSearchReq`/`MsgPaneSearchResp`. Daemon side (`internal/daemon/search.go`): `scanPaneMatches` counts per-line matches + captures the last (most-recent) match as a preview excerpt; `Daemon.searchPanes` scans all panes' loaded `OutputBuf`, never spawns a dormant pane; `paneSearchResponse` (the testable split of `handlePaneSearchReq`) MUST echo `req.Query` VERBATIM — the query is untrimmed and daemon-side normalization would make a whitespace-bearing query look permanently stale. TUI side (`internal/tui/palette_search.go`): 150ms debounce (`paletteSearchDebounce`) coalesces keystrokes; `applyPaneSearch` drops stale responses by comparing the daemon's echoed query to the current `m.palette.query`, and stores each hit AS a `palActGoToPane` `paletteCommand` (label via `paneNavLabel`/`formatPaneNav`, `N×`[` capped`] detail from the PER-HIT `PaneSearchHit.Truncated`, `excerpt` for the preview line). `paletteDisplay()` (palette.go) assembles the ONE list the cursor walks: filtered commands, then — for a non-empty query — a dim `Found in panes` header + the hit rows (or a single dim status row: `Searching…` / `Search timed out — is the daemon running?` / `No matches in any pane`; the payload-level `Truncated` renders as a trailing "some panes hit the cap" note). Because hits are `palActGoToPane` rows, cursor nav (`nextSelectable`/`clampPaletteCursor`), Enter dispatch (`executePaletteCommand` → shared `goToPane`), and row rendering (`renderPaletteLine` + the `excerpt` second line) all reuse the command machinery — no separate content view. `paletteSearchTimeout` (3 s `tea.Tick`, a LOCAL timer that must never re-arm `listenForMessages`; both it and the debounce compare on `m.palette.query`) turns a never-answered request — wedged daemon, or a new TUI against a daemon whose `handleMessage` has no case for `pane_search_req` and silently drops it — into the diagnosable timed-out row instead of an endless `Searching…`. Deferred to Phase 2: per-plugin/instance quick-create, `:` command mode, MRU ordering.

## Pane context menu

### Pane context menu

right-click on a pane (no selection active) or `quick_actions` (default `alt+a`; the M1 `ctrl+a` placeholder was rebound — ctrl+a is readline home) opens a per-pane action popup (`internal/tui/ctxmenu.go`) — a compositor overlay via `overlayAt` (compose.go), NOT a dialogScreen. Targets the pane under the cursor (blue `ctxTargetHighlight` border), dispatches into the existing keybinding handler methods (extracted: `openClosePaneConfirm`/`openRestartPaneConfirm`/`beginPaneRename`/`toggleFocusForActiveTab`/`openHistoryForActivePane`), disabled rows greyed (history without `record_history`, lazygit without binary). "Mark attention" SENDS `MsgUpdatePane{PinnedAttention}` — the pin is daemon-owned and persisted (see `projects.md`), so the row must not write `PaneModel.pinnedAttention` itself: `syncPaneMeta` overwrites it on every broadcast, and a local flip would be reverted within 5 s by the git ticker alone. It survives focus (`ackFocusedPane` never clears it; `tabPinnedAttention` colors the tab label, including the active tab) and renders PURPLE 141 — deliberately not `unseen`'s green, which it used to share, because only `unseen` clears itself when you look at the pane. **`ackFocusedPane` clears `unseen` and nothing else**: `blockedSince`/`blockedReason` also survive focus (it runs on every message, including the 100 ms spinner tick, so clearing there destroyed the mark before it could be seen — see `hooks-and-sessions.md`), and `paneRow` suppresses the blocked glyph for the focused pane instead. That is what keeps **"Clear attention"** the only non-agent route to a clear, and therefore the only way to dismiss a stuck `▲` on a pane you are not going to focus; it drops all FOUR marks together, because clearing one leaves the row looking half-worked. Three of them are client-owned and cleared in place; the pin is sent, UNCONDITIONALLY and never gated on the local value — that value reports only what the last broadcast said, so a Mark followed by a Clear before the round trip returned would send nothing and then let the Mark's own broadcast restore the ◆ after the user cleared it. Menu state is `Model.ctxMenu` (zero value = closed), vanished-target close guarded at the top of `Update`, closed on window resize. Right-click with a selection still copies (split-by-selection). Layout: title row = target pane's `paneDisplayName` (width capped by `ctxMenuTitleCap`, truncated at render) + blank separator + items with a blank row at group boundaries only (`ctxMenuItem.gapAfter`: view actions | pane settings | destructive; `ctxMenuState.spaced` auto-falls back to compact when the box exceeds the content height — geometry lives in the `gapsBefore`/`itemContentRow`/`itemAtContentRow` trio). The focus row's label is stateful (Enter/Exit focus mode). Hover-to-highlight works because `View()` switches `v.MouseMode` to `tea.MouseModeAllMotion` while the menu is open (cell-motion never delivers buttonless hover) and back to cell-motion on close.

**A menu row REFUSES when its target is no longer in the ACTIVE tab.** Eight of the ten items dispatch through `activeTabModel().ActivePaneModel()` (shared with the keybinding and palette paths), which is why every entry point focuses the pane before opening the menu — but that establishes the property at OPEN time and says nothing about EXECUTE time: MCP `set_active_pane` (`setActivePaneMsg` → `jumpToPane`) moves the active project AND tab, and the vanished-target guard at the top of `Update` closes only a menu whose target is GONE, not one whose active tab moved — so Rename seeded the on-screen pane's name, Mute toggled it, and Restart/Close armed a confirm for it. Keyboard and mouse cannot reach that state; MCP is the one producer that can. `executeCtxMenuItem` therefore tests `proj != m.cur() || tabIdx != m.activeTabIdx()` BEFORE the `ActivePane`/`Active` sync, so a refused execute leaves nothing half-applied on a background tab, and it refuses ALL ten rows — including the two attention items that resolve `paneID` directly and could still have acted correctly, because "two of ten rows work after the tab moved" is a rule nobody can hold and the remedy is a second right-click. A future entry point that opens this menu on a pane outside the active tab without focusing it first will find every row inert: focus first, rather than widening the guard.

## Claude resume picker

### Claude resume picker (setup dialog "Session" field)

`[command] sessions = "claude"` plugin opt-in (`claude-code.toml` schema_version 9; `""`/`"claude"` valid, unknown fails plugin load, and `sessions` without `prompts_cwd` ALSO fails — the listing is scoped to the selected directory, so the pair is rejected rather than rendering a field that can never list anything) inserts a `"session"` field in `setupFieldKind`/`setupFieldCount`. Field order is CWD → kube → toggles → worktree → session → Continue: session sits after the worktree field (a `prompts_cwd` picker over the directory's existing git worktrees, added ahead of it in the same ordering) because the session listing is scoped to whichever directory the worktree choice settles on, not just the browsed CWD; session is LAST because it is the only field that expands, so focusing it cannot shift the fixed-height rows above. IPC pair `MsgClaudeSessionsReq{CWD}`/`MsgClaudeSessionsResp{CWD,Sessions,Truncated,Error}` (`internal/daemon/claudesessions.go`): `handleClaudeSessionsReq` runs on a WORKER GOROUTINE (file I/O — same rule `MsgStageUpdateReq` follows) behind a `sessionScanning` single-flight atomic (also `updateStaging`'s precedent — one scan is up to 200×64 KiB of reads, so an unguarded handler lets a looping client stack fd-holding goroutines until the daemon starves; the rejection still echoes the CWD or the TUI drops it as stale). `claudeSessionsResponse` is the pure decode→scan→annotate→echo split; it scans `EvalSymlinks(req.CWD)` because `handleCreatePane` resolves before spawning and claude keys its project dir off the RESOLVED path (scanning the raw value lists an empty directory whenever the user browsed through a symlink), but `CWD` echoes VERBATIM — that contract is the TUI's staleness check, not a statement about what was read. `liveClaudeSessionIDs` marks sessions held by a live pane: captures `(paneID, type, session_id, running)` under `PluginMu`, releases, THEN reads hook id files off-lock (`readHookSessionIDFn` wins over `PluginState`, which is only refreshed at shutdown and reports a pre-rotation id); only panes with a live PTY count, or an exited pane would hold its transcript hostage forever. Spawn path: `CreatePanePayload.ResumeSessionID` → `d.applyResumeSessionID`, which rejects on TWO grounds, each degrading to a fresh session — a non-canonical-UUID shape (it reaches argv; logged by LENGTH only, and the loose `^[0-9a-fA-F-]{32,64}$` used elsewhere would admit all-dash/leading-dash flag-shaped tokens) and a session a live pane already holds.

**That second check is where the "already open" guarantee actually lives** — the TUI greys those rows out, but that is presentation: any IPC client can send the id directly, and even the TUI fetches its listing at T0 and commits at T1. The occupancy test and the write it gates run under `Daemon.resumeClaimMu` as ONE atomic step, and consult `claimedClaudeSessionIDs` (= live panes PLUS panes that have claimed a session but have no PTY yet) rather than `liveClaudeSessionIDs` (running only, which is what the picker DISPLAYS). Both halves are required: `handleCreatePane` runs on the requesting conn's dispatch goroutine, so two clients racing on one session would otherwise both see it free — neither has spawned, so neither is visible to the other — and both would spawn `--resume` on one transcript. `handleReplacePane` therefore claims only AFTER `ReplacePane` publishes the pane, or its claim is invisible to the racing caller. Exited panes never count (their transcript is free). Then → `PluginState["resume_session_id"]` → `resolveSpawnArgs(p, pane, restoring, resumeID)` emits `--resume <id>` INSTEAD of the preassign_id `StartArgs` (`--session-id <new>` + `--resume <existing>` are contradictory), after `InstanceArgs` so toggles still compose. `resumeID` is a PARAMETER, captured by `spawnPane` under `PluginMu`, never read from the map inside `resolveSpawnArgs` — a concurrent map read/write is a fatal runtime throw and the scraper + `refreshPluginStateFromHooks` are live writers. `spawnPane` seeds `session_id` from it rather than minting a UUID, and — because `handleRestartPaneReq` also spawns with `restoring=false` — prefers a hook-recorded id over a stale creation-time pick, retiring the key so Alt+R reattaches to the CURRENT conversation rather than the one chosen days ago. `refreshPluginStateFromHooks` deletes the key once the hook confirms the pane's own session, so it can only ever cover the first-boot gap. `claudeResumeTemplate` falls back to it ahead of `--continue` (a restart before the SessionStart hook fires would otherwise attach to the most-recent session in the CWD, i.e. the one NOT chosen). TUI (`internal/tui/sessions.go`): field is collapsed to one line until focused, `ensureSessionScan` fires on first focus per CWD (a fresh pane costs zero session I/O) and RETRIES after a timeout/failure (only `scanning`/`ready` are treated as settled — the timeout message invites the retry it would otherwise refuse), 3 s local timeout tick (must NOT re-arm `listenForMessages`; the `claudeSessionsRespMsg` branch MUST). `sessionVisibleRows()` shrinks the list on a short terminal because `renderDialog`'s `lipgloss.Place` does not clip and a fixed second full-height list pushes `[Continue]` off-screen. Row width comes from `setupTextWidth()` = `setupDialogWidth() - setupBoxChrome` (6 = 2 border + `Padding(1,2)`'s 4), the single budget every setup-dialog line derives from — lipgloss draws the border INSIDE `.Width` (same accounting as `paletteInnerWidth`), so the older `width-4` reading left every row two cells past the wrap limit and reflow dropped each row's last word onto its own line at column 0. `TestSetupBoxChrome_MatchesLipglossWrapLimit` pins the constant two-sidedly against lipgloss's actual behaviour (too small wraps; too large truncates rows early, which no screenshot reveals). Blocked rows truncate the TITLE and keep the `[open in …]` marker — appending it and truncating the whole row dropped the marker off exactly the long rows that needed it. In-use rows are rendered but Enter is refused — the cursor still lands on them so the footer explains why (Ctrl+N greyed-plugin precedent, not the palette's skip). Changing the CWD clears the choice in BOTH `ensureSessionScan` and `submitSetupDialog` — the submit-time guard is the load-bearing one, since the user can move the browser and press Continue without ever re-focusing the field.

**Detail panel (`i`)**: second IPC pair `MsgClaudeSessionDetailReq{CWD,SessionID}`/`MsgClaudeSessionDetailResp` → `claudesessions.ReadDetail` (worker goroutine, own `sessionDetailReading` single-flight — sharing `sessionScanning` would fail the panel exactly when a listing is in flight, which is when it opens). The session id is a FILENAME COMPONENT, so it is validated against `resumeSessionIDRe` at the handler and re-checked for separators in `ReadDetail`. Reads stream the whole transcript (the last prompt is only knowable at the end) but reject each line by byte-compare before any unmarshal — 88 MB in ~1 s. Only `promptSource=="typed"` entries count: claude records a tool RESULT as a `type:"user"` entry, and an assistant-entry count was tried and dropped (11638 against 87 prompts, because each tool call is its own entry — and confirming those entries was what made the scan 20× slower). TUI state is `Model.sessionDetail sessionDetailPanel` (zero value = closed, the `ctxMenu`/`palette` shape); the panel REPLACES the list in the same field (no overlay plumbing) and is height-capped to `sessionVisibleRows()+1` so opening it cannot grow the dialog. Responses are matched on BOTH echoed keys (id + CWD) because the cursor keeps moving while a read is in flight; `↑`/`↓` re-request for the newly highlighted row. Esc is intercepted in `handleCreatePaneSetupKey` BEFORE the dialog-wide Esc branch, or the first Esc would abandon pane creation

## Input history

### Input history (AI panes)

`internal/panehistory/` — per-pane store of submitted user prompts at `~/.quil/history/<paneID>.jsonl` (one JSON `Entry{v,ts_ms,session_id,text}` per line; `Append` skips empty/whitespace and caps text at 64 KiB rune-safe with `…[truncated]`; `Read` uses `bufio.Reader` (no line-length cap) and skips malformed/partial lines; `Compact` ring-trims to `MaxEntries`=200 via temp+rename; `PreviewLine` flattens one entry to a SINGLE display line — every whitespace run collapses to one space and C0/DEL/C1 are dropped, because the row is drawn inside a fixed-width bordered modal and a prompt is free text a user can paste an ANSI escape into; U+009B is the C1 CSI introducer, which no `r < 0x20` filter catches. Ranging a Go string turns an invalid byte into `utf8.RuneError`, so the output is always valid UTF-8 for lipgloss to measure).

**Synthetic-turn filter**: Claude Code fires `UserPromptSubmit` for machine-injected turns too — a finished background Task resumes the loop by submitting a `<task-notification>…</task-notification>` block, and a subagent reporting to its parent arrives as `<agent-message from="…">…</agent-message>`; both would otherwise pollute history (the second was the one users actually saw filling the list). `IsSyntheticPrompt` (trimmed text must BOTH open with SOME known tag — each open tag omits the closing `>` so an attribute still matches — AND close with SOME known end tag, so a real prompt merely quoting a tag is preserved) gates all three paths.

**The two ends are matched INDEPENDENTLY, not as a pair**: with parallel subagents one turn carries a `<task-notification>` and an `<agent-message>` concatenated, and a pair-wise test matches neither (the first tag's open hits but not its close, the second's close hits but not its open) — letting exactly the noisiest machine turns through. No real prompt both starts with one of these tags and ends with one. The filter runs on: `Append` skips recording it, `Read` filters it (via `readRaw`+`filterSynthetic`, so pre-existing junk never displays and the `MsgPaneHistoryEntryReq` fetch can't resolve it), and `Compact` drops it when it rewrites. `Compact` rewrites ONLY when the number of REAL (post-filter) entries exceeds `keepLast` — gating on the raw line count would let historical junk push a few-real-prompt pane over the cap and trigger a needless rewrite that races the hook's cross-process `O_APPEND` (losing a concurrently-appended prompt). Because `Append` no longer records synthetic turns, on-disk junk is a finite non-growing residue, purged only as a side effect of a genuine over-cap trim of real entries. Source is hooks only — the Claude `UserPromptSubmit` hook (`claudehook/runhook.go`) appends the full prompt when `QUIL_RECORD_HISTORY=1`, set at spawn for plugins with `[command] record_history = true` (claude-code; **OpenCode is a follow-up** — its `chat.message` handler doesn't yet extract message text). Entries are keyed by `ts_ms` (the stateless hook can't compute a seq). Daemon serves two IPC pairs: `MsgPaneHistoryReq`→previews (newest-first, opportunistic `Compact` on read) and `MsgPaneHistoryEntryReq`→full text by `ts_ms` (`Found=false` if compacted away). History survives daemon restart (NOT truncated like the event spool) but is unlinked in `cleanupPaneArtifacts` on pane destroy. TUI: `internal/tui/history.go` mirrors the memory-dialog pattern — `dialogCommandHistory` modal (opened via `command_history` keybinding, default `alt+shift+i`; in `notesKeyExempt`) lists the active pane's previews; `Enter` fetches full text and opens it in the existing read-only log-viewer editor via `openReadonlyText(label, content)`. Every `historyListMsg`/`historyEntryMsg` Update branch MUST re-arm `m.listenForMessages()` (like `memoryReportMsg`) or the IPC listen loop dies. Unsupported pane → empty state. `internal/panehistory` is stdlib-only so the hot-path hook subprocess can import it.

**List geometry**: box is `historyDialogWidth`=100 and rows budget `inner - historyRowPrefix` where `inner = dialogInnerWidth(m.width, historyDialogWidth)`; the shipped version budgeted `boxW-4`, so every row sat two cells past lipgloss's wrap limit and reflowed onto a second line. `dialogInnerWidth(termW, boxW)` (dialog.go) is now the ONE place renderDialog's terminal clamp and the `dialogBoxChrome`=6 subtraction live — `paletteInnerWidth`, `historyInnerWidth` and `setupTextWidth` all derive from it, because a copy that drifts reintroduces exactly that reflow silently while the other copies' tests stay green. Every status line (`Loading…`, the timeout message, the unsupported/empty messages) truncates to `inner` too: at `minTermWidth`=40 the box clamps to 38 and inner to 32, shorter than the unsupported message, and a reflowed line eats one of the chrome rows the height budget assumes. `historyMinRows` is **1, not a friendlier number** — `lipgloss.Place` does not clip, so any floor above the height actually available manufactures the overflow it looks like it prevents (a 3-row floor forced a 10-row box onto 6-9-row terminals, each of which had room for a shorter one). `historyWindow(total, cursor, scroll, visible)` is pure and is called by BOTH `syncHistoryScroll` (after every cursor move) and `renderCommandHistory`, because render must not depend on Update having run — a `WindowSizeMsg` can change the row budget between them. It re-derives the origin from the cursor and clamps to `total-visible` AFTER, in that order: a stored scroll can outlive the list it was computed for and would otherwise draw blank rows under the final entry.

**The entry viewer is the one read-only buffer that opts into `SoftWrap`** (`openReadonlyText`, which also opens at the top rather than the log viewer's end-of-buffer): a prompt is frequently one very long logical line, and with hard truncation everything past the right edge is unreachable — including unreachable to the selection the user opened it to copy, since there is no horizontal scroll. `SoftWrap` must be set BEFORE the position, since it makes `ScrollTop` a VISUAL row index. Mouse selection in that viewer lives in `internal/tui/viewer_mouse.go` + `logViewerPosAt` (model.go, beside `notesEditorPosAt`); `viewerOwnsMouse()` is checked FIRST in every mouse branch of `Update` because `View()` paints the full-screen viewer over panes, sidebar and lazygit overlay alike, so input priority has to match paint priority. Immediately after it sits `modalSwallowsMouse()` (= `m.dialog != dialogNone`), which fixed a **pre-existing bug affecting every dialog**: `View()` renders ONLY the dialog while one is open, yet the four mouse branches had no dialog guard, so a left-press inside a modal armed `hitTestSplitBorder` and the release ran `finishSplitDrag` — moving a split ratio, resizing two PTYs and persisting the layout to the daemon with no visible feedback; a press at row 0 reached `hitTestTab` and switched tabs behind the modal. Order is load-bearing: the viewer IS a dialog, so a blanket swallow ahead of `viewerOwnsMouse` would take back its drag-selection. `newLogViewerEditor` has a POINTER receiver purely so it can `clearDragState()` — terminals routinely drop the release when the button comes up outside the window, and nothing on the close path resets `viewerMouseDown`, so the next viewer's first hover resumed the previous drag from a document position in a different buffer.

**`historyReqTimeout`** (3 s, `historyTimeoutMsg` → `applyHistoryTimeout`, `r` to retry) bounds the list request: `loading` was otherwise cleared only by `applyHistoryList`, so a response that never arrives — dropped, or rejected by `DecodePayload`, which `listenForMessages` answers with a bare `listenContinueMsg` — left the modal on `Loading…` forever. It is a LOCAL timer and its Update arm must NOT re-arm `listenForMessages` (same rule as `paletteSearchTimeout`/`sessionScanTimeout`). `scrollViewer` measures its bottom stop against `visualLayout`, not `len(Lines)` — with wrapping, one prompt is a single logical line spanning many screen rows. The selection primitives (`clampPos`/`setCursorAt`/`beginSelectionAt`/`extendSelectionAt`) sit on `TextEditor`; `NotesEditor`'s exported `SetCursor`/`BeginSelection`/`ExtendSelection` delegate to them.

**Sanitization is on BOTH sides of the socket, following the `claudesessions` precedent** — a recorded prompt is free text the user pasted into, and neither the list row nor the full-screen viewer passes through the VT emulator that makes pane output safe (a full-screen editor is not a pane), so an OSC 52 in a prompt would set the system clipboard on re-read. Daemon side: `PreviewLine` drops Cc **and Cf** (bidi overrides/isolates and ZWSP are printable to `IsControl` and invisible to `IsSpace`, so they defeat both the control filter and the whitespace collapse — and the row is what the user reads before pressing Enter). Client side: `applyHistoryList` re-runs `claudesessions.SanitizeTitle` on every arriving `Preview` and the `historyEntryMsg` arm runs `SanitizePrompt` on the full text, because under `--remote` the daemon is on a host the user may not control and the version handshake proves the binaries match, not that the peer is honest; `truncateToWidth` is ANSI-aware, so an escape measures zero cells and survives truncation intact. `SanitizePrompt` (not `SanitizeTitle`) for the viewer: line breaks are most of a prompt's readability, and its tab→space mapping is needed anyway since the editor does not expand tabs and a literal one drifts the columns its selection math assumes

## Settings persistence

### Settings dialog persistence

every Settings setter (snapshot interval, ghost dimmed, ghost buffer lines, mouse scroll lines, page scroll lines, log level, show disclaimer) flips `m.configChanged = true` so edits survive `cmd/quil/main.go`'s `if m.ConfigChanged()` check on TUI exit. Earlier versions only flagged the disclaimer field, silently dropping every other Settings edit. Log-level changes apply on the next launch (no live re-init); the file handle owned by `main.go` isn't re-plumbed into the Model.

**Stop daemon** is NOT a Settings row — it lives on the F1 → About (root) menu as item index `aboutStopDaemonIndex` (9, last), alongside Settings/Shortcuts/Plugins/Processes/log viewers (handled in `handleAboutKey`). Selecting it transitions to `dialogConfirm` with `confirmKind = confirmKindShutdown`.

**`y` (not Enter) is required to accept** — Enter is the universal commit/toggle key, so reserving it from the shutdown confirm prevents finger-memory misclicks from killing the daemon and every pane child. The Enter/`y` handler sends `MsgShutdown` **synchronously** via `m.client.Send` (not via `tea.Batch` which gives no ordering guarantee and would race `main.go`'s `defer client.Close()`), then returns `tea.Quit`. Final snapshot is written in the daemon's stop defers and panes respawn on next launch. Esc on the shutdown confirm returns to the About menu with the cursor restored to `aboutStopDaemonIndex`. The TUI's Model.client field is the local `tuiClient` interface (Send + Receive) so tests can inject a `fakeSender` — `*ipc.Client` satisfies it implicitly

## Editors and notes

### TOML editor

`internal/tui/editor.go` — full-screen multi-line text editor with rune-aware cursor, TOML syntax highlighting (comments grey, sections orange, keys blue, strings green), TOML validation on save, text selection and clipboard support. Accessible via F1 → Plugins → select plugin. `TextEditor.Highlight` field selects the highlighter (`"toml"` default, `"plain"` for notes). `TextEditor.SoftWrap` (opt-in, default false) makes long logical lines wrap onto the next visual row instead of hard-truncating with a `~`. When on, `ScrollTop` is a visual-row index and all per-keypress math goes through `visualLayout(contentW) []visualRow` (character wrap, not word wrap). Helpers: `cursorVisualRow` maps the cursor's `(CursorRow, CursorCol)` to a visual-row index (cursor on a wrap boundary attributes to the continuation row, except at end-of-logical-line); `visualToLogical(layout, vrow, vcol)` is the inverse used by mouse-click translation in `model.go:notesEditorPosAt`; `verticalMove(dir)` walks visual rows; `contentWForLayout()` is the single source of truth for `ViewWidth - gutter - 1` (floor 10). Only `NotesEditor` opts in — the TOML editor and F1 log viewer keep truncation. Soft-wrap selection rendering intersects `Sel.ColRange` with each visual row's `[Start, End)` window, so shift-arrow selections remain contiguous across wrap boundaries

### Pane notes

`internal/tui/notes.go` — `NotesEditor` wraps `TextEditor` in plain-text mode (`HighlightPlain`). Intercepts `Ctrl+S` (calls `persist.SaveNotes`, bypassing TOML validation) and `Esc` (clears selection first, exits on second press). Public selection API: `SetCursor`, `BeginSelection`, `ExtendSelection`, `HasSelection`, `ExtractSelection`, `ClearSelection`. 30s debounce via `notesTick` Bubble Tea timer — `MaybeAutoSave()` checks `time.Since(lastEditAt)` on each tick. Storage: `internal/persist/notes.go` at `~/.quil/notes/<pane-id>.md` with atomic `os.CreateTemp`+rename, `Lstat` symlink rejection, and Windows reserved-name validation. Model state: `notesMode`, `notesEditor`, `notesPaneFocused`, `notesEnteredFocus`, `notesMouseDown`, `notesAnchorRow/Col`. Layout math (sidebar + notes panel widths) lives in a single helper `notesPanelWidth()` shared by `View()` and `notesEditorBox()`.

**Auto-enters focus mode** so the bound pane fills the available area on the left; the editor takes ~40% on the right.

**Tab/Shift+Tab cycles keyboard focus** between editor (default) and the bound pane — editor focused = bright blue border + keys to editor; pane focused = dim grey border + keys to PTY. Mouse: click in editor positions cursor + focuses editor; click+drag selects (anchor resolved once at click time, stored in `notesAnchorRow/Col` so scroll cannot drift it); right-click copies selection (notes selection takes priority over pane selection); click in pane area focuses the pane. Key routing: `Alt+E` exits, `Ctrl+Q` quits with flush, `Tab`/`Shift+Tab` cycle focus, structural keys (`Ctrl+W`/`Alt+W`/`Alt+Shift+H`/`Alt+Shift+V`, plus directional `Alt+Arrow` pane-nav) flush + fall through, `notesKeyExempt` allow-list of global shortcuts (rename/dialogs/F1/`Alt+1..9`/etc.) bypass the editor when editor-focused.

**Single canonical teardown** in `exitNotesModeInPlace` (pointer receiver) — `exitNotesMode`, `applyWorkspaceState` reconciliation, and `switchTab` all delegate to it. The reconciliation also re-syncs `tab.ActivePane = bound` if the daemon promoted a different pane, so the editor stays next to its target. `main.go` calls `model.FlushNotes()` on TUI exit as a safety net

### Editor selection

`internal/tui/editor_selection.go` — `EditorSel`/`EditorPos` types (rune-based, independent from terminal `Selection`). Shift+Arrow char select, Ctrl+Shift+Arrow word jump, Ctrl+Alt+Shift+Arrow 3-word jump, Shift+Home/End line select, Ctrl+A select all. Enter copies selection, Ctrl+X cuts, Ctrl+V pastes (async via `editorPasteMsg`). Selection rendering via reverse video `\x1b[7m]`, cursor within selection uses `\x1b[7;4m]` (reverse+underline). Typing with selection replaces selected text


## Processes dialog

### F1 → Processes (replaces F1 → Memory)

`internal/tui/processes.go` + `internal/proctree/` + `internal/daemon/procreport.go`.
Row 3 of the About menu was RELABELLED, not added: the menu is index-addressed
and `aboutUpdateIndex`/`aboutWhatsNewIndex`/`aboutStopDaemonIndex` are named
constants below it, so inserting a row would have moved all three including the
destructive shutdown-confirm routing.

**Nothing here infers process identity.** The previous attempt (`ab3ac99`,
removed from PR #177 before merge) scanned the CLIENT's process table and
matched image paths: on Windows `Cmdline` came from
`QueryFullProcessImageNameW` so the `mcp` token never matched, on Unix orphans
reparent to PID 1 so the liveness check never fired, and `IsBridge` substring-
matched `"quil"` against a whole path — which this repo's own directory
satisfies. All of it was also the wrong MACHINE under `--remote`. The daemon
spawned the PTY children, so it passes their PIDs to `proctree.Build` as roots;
quil's own processes self-report over the socket (`MsgClientHello`). There is no
classification left to be wrong.

**Depth 1 is the pane's own child and is never killable** — that is
restart-pane. `K` (uppercase; lowercase `k` is cursor-up, and binding a
destructive action to a navigation key is how a user kills a process while
scrolling) acts only on `Depth >= 2`, and the daemon re-derives the tree and
re-checks before signalling anything. The client's request is a proposal.

**`CPUPct` is negative for unknown, never 0**, all the way from `proctree` to
`formatCPU`'s em dash. A first sample, a newly-appeared process, a recycled PID
and an unsupported platform all mean "no answer"; `0%` reads as idle, which is
the wrong claim in a dialog for finding something that spins. Darwin's figure is
a kernel decaying average rather than a delta over our window
(`CPUSampled=false`), and the dialog footnotes that — a column that looks
uniform while meaning different things per platform is exactly the
confidently-wrong answer this feature exists to remove.

**`WithTrees` gates two things at once**: whether trees are on the wire, and
whether the daemon's collector runs at all. The status bar polls the SAME
message every 5 s for the life of the session and must never set it — trees for
forty panes are tens of kilobytes per report, and that frame on the 64-slot
must-deliver queue is the documented force-disconnect shape. The collector's
gate is a decaying deadline these requests renew, NOT a close message: a client
that crashes mid-dialog never sends one, and a renewed deadline cannot leak
because every lost message stops it.

**The single-flight MUST keep its timeout.** Collector renewals ride the same
requests, so an unbounded suppression would freeze refresh and starve the gate
together on one lost response.

`applyResourceReport` updates the status-bar total unconditionally but touches
dialog state only under `m.dialog == dialogProcesses` — the removed version
wrote `dialogCursor` unguarded, so a late scan moved the About cursor. Rows are
sized against `dialogInnerWidth`, not a literal: the removed version emitted
89-cell rows into an 86-cell budget and every row wrapped.

**The row list SCROLLS, and that is not optional.** `renderDialog` places the
box with `lipgloss.Place`, which does not clip — this file documents that in
several other places. A 33-tab workspace produces ~42 rows before anything is
expanded, so an unwindowed list draws past the bottom of the terminal and the
footer is simply gone, while the cursor still moves into rows nobody can see.
`procWindow` is the same pure shape as `historyWindow` and is called by BOTH
`syncProcScroll` and the renderer, because render must not depend on Update
having run.

**Every column is bounded in CELLS, and the assembled row is clamped again.**
`padCell`/`padCellRight` exist because `fmt`'s `%-*s` pads to a RUNE count while
`truncateToWidth` measures cells: 构建 is 2 runes and 4 cells, and
`sanitizeRemoteText` preserves printable non-ASCII byte-identically, so a remote
host's process names reach this path unchanged. The NUMERIC columns are bounded
too — PID, CPU and RSS all come off the wire, and a PID of `math.MaxInt64` is 19
characters into a 7-cell column. The final `truncateToWidth(line, inner)` in
`procLine` is a guarantee independent of the column arithmetic, which cannot
satisfy a narrow terminal on its own (`nameW` has a floor, so below ~48 cells
the fixed columns already overflow).

**`clampDepth` is a crash guard, not tidiness.** `ProcNode.Depth` is a plain int
decoded off the socket and the indent is `strings.Repeat("  ", depth+2)`, which
PANICS on a negative count — so a daemon answering `"depth": -3` kills the TUI
the moment the user expands a pane. Verified empirically.

**Nothing that blocks runs on the IPC dispatch goroutine.** `handleConn`
processes one connection's messages sequentially, so a parked handler stops that
client's keystrokes to every pane. Both the collector's first `collect()` and
the whole kill path (enumerate → verify → sweep) run on worker goroutines,
following `handleClaudeSessionsReq`'s precedent, each behind a single-flight.
The graceful pass is NOT cheap on Darwin: verifying identity forks `ps` per
process, so a subtree kill is one fork per node.

**A treeless response must not replace a tree-bearing one.** The status bar and
the dialog share `MsgResourceReportReq`, so a status-bar poll can be in flight
when the dialog opens; the response echoes `WithTrees` so the client can tell
them apart. Inferring it from a populated field instead would mistake an empty
tree for a treeless answer.
