## Remote-correct filesystem dialogs

### Remote-correct filesystem dialogs (Phase 3, RD-020/RD-021/RD-028)

every dialog that touches a filesystem now asks the DAEMON, because the local disk is the wrong machine whenever the daemon is remote. Two IPC pairs — `MsgBrowseDirReq/Resp` (`internal/daemon/browse.go`) and `MsgGitReposReq/Resp` (`internal/daemon/discover.go`) — each on a worker goroutine behind its OWN single-flight atomic (`browseScanning`/`gitDiscovering`; separate slots because the setup dialog resolves a directory and then scans it for repos, so one shared guard would make each step fail exactly when it followed the other). The daemon owns every decision that describes its own machine: the `Child` join (separators belong to the machine holding the disk), `~` expansion (`expandHome`), `filepath.Abs`, filesystem roots (`browse_roots_windows.go` / `_other.go`), and existence. Six wrong-machine bugs in `dialog.go` fell out of this — the join, `~` via the local `os.UserHomeDir`, `filepath.Abs`, `os.ReadDir` in the CWD browser, `gitdiscover.Candidates` in Alt+G, and the home candidate.

**CONTRACT: responses echo the request key VERBATIM** (`Path`, `Child`, `CWD`) on every path INCLUDING the error and single-flight-rejection ones — it is the client's staleness key, not a statement about what was read, so daemon-side normalisation would make a live request look permanently stale. The rejection must carry BOTH halves of the browse key: the client matches on `(Path, Child)` together, so a rejection echoing only `Path` is dropped as stale by every descend — which is the common case, since that is what clicking a folder sends — and the field then waits out its whole client-side timeout for an answer it already holds.

**Requests carry a per-request generation in `ipc.Message.ID`**, echoed by the existing `respondTo`: a purely client-side counter cannot fix response crossing, because two daemon responses for the same content key are wire-indistinguishable. `browseState` (`internal/tui/browse_client.go`) needs an explicit `pending` flag where `repoScanState` (`discover_client.go`) does not — `""` is a VALID Path (the daemon's default CWD), so the zero value cannot double as the idle sentinel; that one constraint is why `applyBrowseDir` does not zero on a match and why `applyBrowseTimeout` must gate on `pending` as well as the key, or a request's own late tick overwrites the listing it just delivered. Entries are sorted dirs-first BEFORE the `MaxBrowseEntries` cap, which makes the cap able to drop only trailing FILES — capping `os.ReadDir`'s name order instead returns 500 files and no folders in a large directory, dead-ending the browser on a directory that visibly has folders in it.

**ONE deadline is shared by the directory read and the symlink resolution that follows it**: `os.Stat` follows the link so it parks on a dead mount exactly as `os.ReadDir` does, and it runs while the single-flight slot is still held — a budget covering only the read moves the wedge one syscall later rather than preventing it. Sharing the deadline also makes the timeout self-propagating: a stat that times out has by definition spent the budget, so every later link sees a non-positive one and classifies from its directory record without a syscall, capping the cost of a directory full of dead links at ONE abandoned goroutine rather than one per entry (an explicit stop-resolving flag was tried and removed — it could only fire in states the deadline already covered). `maxBlockingFSCalls` bounds abandoned readers process-wide, because a goroutine parked in a syscall pins an OS thread and the runtime aborts past 10 000 — a daemon runs for weeks, so a client re-driving navigation into a mount that never answers otherwise has an unbounded path to killing every pane. `statPath` is the seam that makes the never-answers case testable at all.

**The Windows root sweep is the ONE call site that does not inherit the self-propagating property, and that cost a second P1**: `sweepRoots` (`browse_roots.go`) gives each drive probe its own `rootProbeTimeout` sub-budget, so a timed-out probe leaves the shared deadline almost untouched and the next drive starts a FRESH abandoned goroutine — the per-probe clamp bounds the WAIT, nothing bounded the permit HOLD. Eight dead network mappings (a VPN-off laptop with departmental shares reaches that) drained the whole pool in one sweep, after which browse, git discovery and kube discovery were all refused daemon-wide. `maxRootProbeTimeouts` caps how many probes one sweep may ABANDON — counting unanswered rather than elapsed, because a probe that answers releases its permit immediately and accumulates nothing however many there are; it also covers a refused claim, and sits above 1 so one stale mapping cannot hide every drive behind it.

**That per-sweep cap alone does NOT close it, which is a second P1 on the same file**: nothing returns an abandoned permit but the kernel, so ⌈`maxBlockingFSCalls`/k⌉ successive sweeps still drain the pool and pressing "up" four times is navigation. `probeRoot` therefore claims against `maxRootProbePermits` (via `statIsDirWithinLimit`/`claimBlockingFSCallUpTo`), leaving a reserve the sweep can never touch — which also encodes the priority, since the drive list is a speculative affordance for the "up" row while the read that follows is what was actually asked for. `readDirWithin` gained the `d <= 0` guard `statIsDirWithin` always had, reachable precisely because the sweep runs FIRST on the shared deadline. `sweepRoots` returns `complete` (= every candidate ANSWERED, not "the loop finished" — a timed-out drive is missing just as invisibly as a capped one) → `RootsTruncated`, a SECOND wire flag rather than a reuse of `Truncated`: the sweep can give up while the same response's directory read succeeds, and `showRootsList` swaps the roots flag in when it promotes the roots to BE the listing. `listFilesystemRoots` is a package-var seam because the Unix arm always reports complete, so `out.RootsTruncated = !complete` is statically DEAD on the platform CI runs — inverting it passed every test in the repo until the seam existed. The sweep was split OUT of `browse_roots_windows.go` and takes its probe as a parameter for a reason worth generalising: the earlier fix was shipped as "not directly testable in CI — the Linux image never compiles this file", and a bounded-resource interaction no test can reach is exactly where the next bug lives.

**Security: Phase 3 MOVED A TRUST BOUNDARY.** Filenames, resolved paths, error text and repo paths now come from a host the user may not control. `sanitizeRemoteText` (`internal/tui/remotetext.go`) drops C0/DEL/C1 (including U+009B, the C1 CSI introducer that `internal/tui/oscfilter.go` already exists because of) and bidi overrides/isolates, maps tab to space so rendered width matches measured width, and preserves printable non-ASCII byte-identically. Applied **at render only** — raw values stay in state, because the resolved path becomes the pane's spawn CWD and a repo path becomes lazygit's `--path`. Bidi is the non-obvious half: `U+202E` is *printable*, so it passes any control-character filter while reversing the text on the list the user picks a spawn directory from.

**Phase 3 remainder (RD-022…RD-025) added three more pairs.** `MsgKubeCtxReq/Resp` (`internal/daemon/discover.go`, own `kubeDiscovering` slot claimed through `beginKubeDiscover` — extracted precisely so the slot-independence test exercises the handler's OWN claim path; a test that claims `d.kubeDiscovering` directly stays green when the handler is pointed at `gitDiscovering`); `MsgPluginListReq/Resp` (`internal/daemon/plugins.go`); `MsgDirsExistReq/Resp` (`internal/daemon/browse.go`, own `dirsChecking` slot).

**`dirsChecking` is NOT `browseScanning`, and the reason is timing rather than tidiness**: the client gives up after `recentScanTimeout` (8 s) while the daemon holds its slot for as long as the syscall really runs — up to `browseTimeout` (10 s) when a stat parks — so a shared guard would have the timeout's own `initSetupBrowser()` handover rejected by the request that just timed out, dead-ending the dialog in exactly the dead-mount case the bound exists for. `dirsExistResponse` shares ONE deadline across the whole list, like `classifyEntries`, so a hung mount costs one abandoned goroutine rather than one per path.

**The plugin RPC is REMOTE-MODE ONLY, deliberately** — the daemon detects at start and on reload then runs for weeks, while the TUI detects every launch, so adopting its answer locally would replace a fresh answer with a stale one about the same machine; it also needs no worker goroutine, no single-flight and no per-request generation, because the handler reads an in-memory map under an existing RLock with no filesystem call and every response describes the same daemon (all three omissions are load-bearing choices, not oversights — see RD-029 for why re-detecting on request is blocked on removing `Registry.Get`'s pointer escape). **Each answer is FILED against the daemon that gave it, never adopted into the registry** — `Model.destAvail[dest]`, keyed by `ipc.Message.Origin` (which `Router.pump` stamps on receive and `pluginListMsg.Dest` carries), read through the single accessor `Model.pluginAvailableFor(dest, name)`. The registry's `Available` flags therefore describe THIS machine and no other, and `Registry.SetAvailability` — the one global override — is DELETED rather than merely unused. It was the whole of the 2026-09-03 bug: one registry serves every destination, so the last host to reply spoke for all of them, and adding a remote with no `claude` greyed out Claude Code in the LOCAL project while claude was running on the laptop. Nothing recovered it, because `DetectAvailability` only ever sets availability TRUE. A plugin ABSENT from a host's answer reads unavailable FOR THAT HOST (`spawnPane` would fall back to `terminal` there and the pane would open as a shell wearing the wrong name); an EMPTY response is refused rather than filed (it would grey out everything on that host at once); and a destination that has not answered at all — a reply still in flight, a daemon too old to have the RPC — keeps local detection, because a wrong offer fails loudly at spawn while a wrong grey-out hides a working tool silently. **Every `.Available` consumer goes through the accessor and names the machine it means**: the `Ctrl+N` list, its Enter gate and its sort take `createPaneDialogDest()` (the dialog PINS its destination at open, and that is where the pane is going), the two overlay gates take `tab.Dest` (matching `createOverlay`'s `tabDest`), and the palette, context menu and `F1` → Plugins list take `activeDest()`.

**Every TUI-side `DetectAvailability()` is UNCONDITIONAL** (`dialog.go`'s two plugin-dialog buttons, `migration.go`), and that has now been wrong in BOTH directions. It first ran into the one shared registry and overwrote the daemon's answer with a pass over the wrong machine; the `RemoteMode()` guard added for that then meant a remote session never re-detected — so once answers moved to `destAvail` the same three call sites greyed out every LOCAL plugin instead, since `LoadFromDir` replaces each plugin and `Available` is runtime-only. Only the split fixes both: the registry is re-detected every time because it describes this machine, and no remote answer is in its way. The re-request still rides along, because a reload changed a plugin DEFINITION and the remote is still holding what it reported about the old one — and the reload and the re-request must leave in ONE `tea.Cmd`, since `ipc` dispatches a single conn's messages sequentially but `tea.Batch` runs its children on separate goroutines and guarantees nothing, so a batched pair can be answered from the PRE-reload registry. `config.RecentCWDsPath(dest)`: empty dest keeps `recent-cwds.json` byte-identically so existing installs need no migration; a non-empty one collapses everything outside `[A-Za-z0-9_-]` and appends a digest of the ORIGINAL string — **the digest, not the collapse, is what keeps destinations distinct** (`a/b` and `a-b` collapse alike), and `.` is excluded from the passthrough set so `..` is unreachable by construction rather than filtered.

**`SetRemoteDest` stays PURE**; the per-destination load lives in `cmd/quil/main.go` via `SetRecentCWDs`, because ~46 tests build a `Model` directly and never set `QUIL_HOME`, so a disk read in that setter would point every one of them at the real `~/.quil`. `attachCWD` returns `""` in remote mode — `defaultCWD()` validates and falls back, so sending the laptop's path was safe *by coincidence*, and a path existing on both machines is where the coincidence stops.

**`listenForMessages` decode-error branches return `listenContinueMsg{}`, never `nil`** — `nil` yields no message, so `Update` never reaches a re-arm branch and the listen loop dies for the session on one malformed frame. Kube contexts pass `sanitizeRemoteText` at render like every other remote string, and the field renders scanning / empty / failed apart, because an in-flight scan showing "(no kube contexts found)" is the same confidently-wrong answer this phase exists to remove. Still local, deliberately: plugin *definitions* (RD-035, which also covers the F1 → Plugins editor reading and writing the CLIENT's `PluginsDir()` before telling the remote daemon to reload from its own), availability freshness (RD-029), and `buildPaletteCommands`' local `os.UserHomeDir()` abbreviation of pane CWDs (RD-036)
