Found 2026-08-26 QA'ing PR #195 (`fix/performance` branch, "quil's own processes report their own cpu and rss" feature — see `internal/daemon/procreport.go`, `cmd/quil/hello.go`, `internal/proctree/selfsample.go`). All mutation-verified. **Gaps 1 and 2 were RESOLVED in-branch** after this note was written — see the resolution line under each. Gap 3 is still open and is filed as `techdebt/4-2-proccollector-goroutine-not-tied-to-daemon-stop.md`.

**Gap 1 — `cmd/quil/hello.go`'s `startClientStatReports` (the ticker goroutine pushing `MsgClientStat` every `statPushInterval`) has zero tests, but IS testable.** Proved this by writing a throwaway probe test reusing `clientOverPipe(t)` from `cmd/quil/remote_verify_test.go` (builds a real `*ipc.Client` over `net.Pipe()` via `ipc.NewClientWithDialer` — the pattern already exists in this codebase for exactly this kind of ticker/goroutine test). Calling `startClientStatReports(client)` and reading the raw length-prefixed frame off the pipe end decoded a real `MsgClientStat` after 5s (`cpu=-1 rss=10383360` on first tick, correctly unknown-CPU since only one reading exists). Deleted the probe file afterward (QA agent doesn't write permanent tests). `statPushInterval` is a `const`, not a `var` — unlike `clientSendTimeout` in `internal/ipc/client.go`, which is deliberately a `var` so tests can shrink it. A real test would either eat the 5s real-time cost or need that const loosened to a var first.

**RESOLVED in-branch (commit `b352873`).** `statPushInterval` is now a `var` for exactly this reason, and the loop takes a one-method `statSender` interface, so `cmd/quil/hello_stat_test.go` drives it with a fake at 5 ms ticks instead of over a pipe at 5 s. Tests cover: pushes on each tick with a decodable `MsgClientStat`, stops when the link reports gone, nil sender is a no-op, and a compile-time assertion that `*ipc.Client` still satisfies the interface. The same commit changed what the loop calls — `SendDroppable`, not `Send` — because `Send` closes the conn on timeout and the MCP bridge never redials.

**Gap 2 — the daemon's OWN row in `handleResourceReportReq` (`Role: "daemon"`, fed by `d.procReport.SelfStat()`) has no test at all.** Mutated the call site to skip `SelfStat()` entirely (report `UnknownCPU`/`0` unconditionally) and ran the full `internal/daemon` suite — 100% green, mutation not caught. Grepped every `*_test.go` in the package for `"daemon"` role assertions: zero hits. Every existing test covers `procCollector.SelfStat()` directly (unit) or `hellos.describe()` (client-reported tui/bridge rows) — nothing exercises the assembly step where `handleResourceReportReq` appends the daemon's own row using that same `SelfStat()` call. `TestDaemon_ClientStatRoundTrip` (`internal/daemon/procstat_ipc_test.go`) already proves the pattern works end-to-end for a socket client's row — extending that same test to also assert on the `Role: "daemon"` row in the same response would close this cheaply (the row is already in the response payload it's decoding).

**RESOLVED in-branch (commit `50e46a8`).** `TestDaemon_OwnRowCarriesItsSelfMeasurement` in the same file closes it, and the same `SelfStat()`-skipping mutation now fails with "the daemon's own row never carried an RSS reading". It asserts on RSS rather than a percentage: the first tree request starts the collector, whose first pass has nothing to delta against, so the daemon's own CPU is legitimately unknown for a tick or two — asserting a percentage would be a race against `procTickInterval`. It retries up to three reports for the same reason.

**Gap 3 (side finding, not a test-quality issue) — `procCollector`'s `Renew()`-spawned goroutine is not tied to daemon shutdown.** `internal/daemon/daemon.go`'s `Daemon.Stop()` closes `d.shutdown`, stops the IPC server, waits on `d.collectorWG` (which ONLY wraps `d.memReport.Run(ctx)` — checked directly, `procReport` is never referenced in `Stop()`), snapshots, then closes pane PTYs. `procCollector` has no `Close`/`Stop` method at all; its background goroutine (started by `Renew()` on any `WithTrees: true` request) only exits when its own `procGateWindow` (15s) gate expires. `internal/daemon/procstat_ipc_test.go`'s two integration tests both send `WithTrees: true` against a live `daemon.Start()`, so each leaks this goroutine for up to ~15-20s past `t.Cleanup(d.Stop())`. `dev.sh test-race internal/daemon` came back clean (no detected race) — likely because each test builds its own isolated `daemon.New(cfg)`/session with no shared globals, so the leaked goroutine only ever touches its own now-orphaned daemon instance. Pre-existing production behavior, not introduced by this PR or these tests — just the first tests to exercise it via a real `Start()`/`Stop()` cycle with trees requested.

**Why:** documents a genuine, specific, actionable set of coverage gaps in case this feature area is touched again — so a future QA pass doesn't have to re-derive the mutation results, and so a future feature PR in this area can cite these as known follow-ups rather than re-discovering them.
**How to apply:** If a future PR touches `internal/daemon/procreport.go`, `cmd/quil/hello.go`, or adds a `Close`/lifecycle method to `procCollector`, check whether these three gaps were addressed — if `procCollector` gains a shutdown hook, verify it's wired into `Daemon.Stop()` (grep for `procReport` there, same way `[[project_ipc_write_window_wiring_gap]]` and `[[project_notify_wiring_gap]]` were confirmed by grepping for the call site rather than trusting a wiring claim). If asked to test a similar per-process self-reporting ticker again, start from `clientOverPipe` in `remote_verify_test.go` rather than re-deriving the net.Pipe pattern from scratch.
