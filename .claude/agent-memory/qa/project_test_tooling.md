All tests run via Docker through `./scripts/dev.sh test` (uses `golang:1.25` image). Go is NOT installed locally. Direct `docker run` with `-v quil-gomod:/go/pkg/mod` also works.

- Unit tests: `./scripts/dev.sh test` — runs `go test ./...` inside Docker
- Race detector: `./scripts/dev.sh test-race` — adds CGo + gcc inside Docker
- Platform-specific tests: `//go:build` tags used; Unix PTY tests run in the Linux Docker container; Windows PTY code is NOT exercised in CI (no Windows runner)
- Test files follow Go conventions: `*_test.go` in the same package or `_test` external package
- No test framework beyond stdlib `testing` — plain `t.Fatal`, `t.Error`, `t.Run`

**Why:** No local Go installation — Docker-first tooling policy per `local-environment.md`.
**How to apply:** Always use `./scripts/dev.sh test` when running tests. Never suggest `go test` as a bare command.

## Transient bind-mount glitches on this Windows host

Direct `docker run -v "$(pwd -W):/src" ...` against the repo on this Windows host occasionally serves a stale/inconsistent view of the source tree to a freshly-started container: observed a phantom `go vet` error for a nonexistent file (`open internal/tui/zz_tmp_height_check_test.go: no such file or directory`) and a phantom build failure in a package whose test file appeared to have an old function signature that didn't match the current on-disk source — both vanished on an immediate retry of the exact same command with no code changes in between.

**Why:** Docker Desktop's Windows file-sharing layer (gRPC-FUSE/VirtioFS) for bind mounts can desync briefly, especially right after other containers have just read/written the same mounted path.
**How to apply:** Never report a build/vet/test failure from a single docker run as real without retrying it once first (ideally with `-count=1` for tests to bypass any cache). If a failure disappears on retry with zero source changes, it was the bind-mount glitch, not a code issue — don't mention it in a QA report except perhaps as a footnote. If it reproduces on retry, it's real.

## Worktrees are shared and actively edited by other agents mid-QA

Observed directly (2026-07-31, `fix-input-history-ui` worktree): a `go test -race ./...` run failed with a genuine-looking compile error (`undefined: claudesessions`) referencing a file (`internal/tui/history.go`) that another teammate agent was actively editing at that exact moment (security-review-driven sanitization work landing incrementally). A `git status`/`git diff` taken seconds later showed the file mid-edit — the import and the usage were both present and consistent by the time I re-read it, and a retry of the exact same test command passed cleanly.

**Why:** Worktrees in this multi-agent session are not exclusive to the QA agent — other teammates (main, sec-review, etc.) can be writing to the same files in the same worktree concurrently while QA runs. A build/vet/test failure that mentions a symbol or file that looks unrelated to anything in the diff you were handed is a strong signal you raced a concurrent edit, not a real regression.
**How to apply:** On any unexpected/unfamiliar build failure, immediately run `git status --short` and `git diff --stat` before concluding it's real — if the failing file has uncommitted changes and doesn't match what you were told to review, retry the test after a few seconds rather than reporting it as a bug. Also re-check `git diff --stat` right before your FINAL test run and report against that snapshot, since the working tree can keep moving throughout a QA session — note in the report if scope grew beyond the originally-assigned file list, since that work hasn't been reviewed yet.

## The concurrency also happens in the PRIMARY worktree (`E:/Projects/Stukans/quil` itself), not just `.claude/worktrees/*`

Observed directly (2026-08-01, `fix/remote-stale-binary-record` / PR #118 QA): the repo's MAIN checkout (not a sub-worktree) had live uncommitted edits to exactly the files under review (`cmd/quil/remote_setup.go`, `remote_setup_test.go`) plus two files outside the assigned scope (`internal/remoteinstall/probe.go`, `probe_test.go` — an unrelated bidi-sanitization fix). Two `./scripts/dev.sh test` runs seconds apart against the SAME command gave different results for `cmd/quil` (all-pass, then a genuine `FAIL` with different assertions each time) because another agent was actively rewriting `healRemoteRecord`/`offerRemoteInstall` (adding an `ExistingDirWritable` privilege-escalation gate) mid-flight — not a Docker bind-mount glitch (that class reverts identically on retry; this one changed content between runs).

**How to apply:** If retrying a failure doesn't stabilize it, or two consecutive runs fail differently, suspect a live concurrent edit even when `pwd` is the main repo directory, not a named worktree. To get a trustworthy pass/fail read of the branch AS COMMITTED while someone else edits the same files live: `git worktree add --detach <scratchpad>/qa-clean-<name> <commit-sha>` (an ADDITIVE git op, safe — never `git stash`/`checkout -- .`/`reset --hard` on the shared directory, that would destroy the other agent's uncommitted work), run `./scripts/dev.sh test`/`vet` there, then `git worktree remove --force <path>` to clean up. Report results from that isolated run as the authoritative answer for the PR under review, and separately flag the live uncommitted files (with their paths) as out-of-scope concurrent work the report is NOT evaluating.

## `go test -race` in the Docker container can FAIL once then pass 4/4 on immediate retries, zero code changes

Observed 2026-08-04 (`fix-input-ordering`, `internal/tui`): a fresh `-race -count=1 -v` run reported `FAIL github.com/artyomsv/quil/internal/tui` with no visible `--- FAIL` or `DATA RACE` block in the tail of the output (the failure summary line was the only signal, and it was in a `tail -N`-truncated capture the first time). Four immediate re-runs of the identical command (one full-output capture + three more full package runs including `internal/daemon` and `cmd/quil`) all passed clean. This is a DIFFERENT symptom shape from the already-documented bind-mount glitch (phantom missing-file errors) — this one is a bare `FAIL` on the package line with no diagnosable cause surfacing in a truncated tail.

**Why:** Unconfirmed root cause — could be the same Windows Docker Desktop bind-mount desync as the glitch above, could be a CGo/race-runtime hiccup under `-e CGO_ENABLED=1` + on-the-fly `apk add gcc` in the container. Either way it did not reproduce.
**How to apply:** Never trust a single `-race` FAIL, especially if you only captured a `tail` of the output and can't see an actual `DATA RACE` stack. Re-run the exact command with FULL output capture (no tail truncation) at least once before reporting a race as real; if it was a real race the stack trace reproduces every time. If it passes clean on retry with zero source changes, treat the first result as noise and don't report it as a finding — but do mention in the QA report that one transient race-detector FAIL was observed and did not reproduce across N retries, so the reader has the full picture.

## `dev.sh test`/`test-race` report `(cached)` per-package — force a truly fresh run to back a "PASS" claim

`./scripts/dev.sh test` runs `go test ./...` with no `-count=1`, so Go's content-addressed test cache returns `(cached)` for any package whose files hash-match a prior run (legitimately still correct — it's keyed on content, not time — but it isn't evidence you just now executed those tests, which matters when a report says "ran tests and saw X").

To force a fresh, verbose, single-package run without touching `dev.sh`, replicate its docker invocation directly:
```bash
PROJECT_DIR="$(pwd -W 2>/dev/null || pwd)"
docker run --rm -v "${PROJECT_DIR}:/src" -v quil-gomod:/go/pkg/mod -v quil-gocache:/root/.cache/go-build \
  -w //src golang:1.25 go test -count=1 -v -run 'SomeTestPattern' ./internal/somepkg/...
```
(`-w //src` — double slash — because Git Bash mangles a single-slash `/src` into a Windows path; `dev.sh` itself hits this, hence its own `-w //src`. Reusing the wrong pwd form, e.g. plain `pwd` in Git Bash context, produced `docker: ... working directory 'C:/Program Files/Git/src' is invalid` — `pwd -W` gives the real Windows path.)

**How to apply:** For a QA report claiming specific new/changed tests pass, run them via this direct invocation with `-count=1 -v -run <pattern>` (isolated from the rest of the suite) so the transcript shows real `=== RUN` / `--- PASS` lines, not a cache hit. Reserve the plain `./scripts/dev.sh test`/`test-race` (which may report cached results) for confirming the whole suite is green, and note in the report which parts were freshly re-verified vs. relied on cache.

**If you hand-roll the `docker run` for `-race` (bypassing `dev.sh test-race`), the base image must match `dev.sh`'s `GO_IMAGE` exactly — `golang:1.25-alpine`, not `golang:1.25`.** Confirmed 2026-08-05: building a race image with `FROM golang:1.25` + `RUN apk add --no-cache gcc musl-dev` fails (`apk: exit 127` — Debian-based `golang:1.25` has no `apk`). `dev.sh`'s own `ensure_race_image` builds `quil-race:$(GO_IMAGE translated)` from `golang:1.25-alpine`, where `apk` exists. Simplest fix: don't hand-roll it — `cd` into wherever you want race results from (a worktree included) and run `./scripts/dev.sh test-race` there; it resolves `PROJECT_DIR` from its own script location, so it works correctly from any checkout, not just the primary one.

**`dev.sh test`/`test-race`/`vet`'s package argument is a BARE package path, not a `go test` pattern — `pkg_target` appends `/...` itself.** `./scripts/dev.sh test-race ./internal/tui/...` silently no-ops (`go: warning: "./internal/tui/.../..." matched no packages` / `no packages to test`) because the trailing `/...` gets doubled. Pass `internal/tui` (no `./`, no `/...`); `dev.sh` turns that into `./internal/tui/...` internally. This is also why `-run`/`-v`/other `go test` flags can't be threaded through `dev.sh test` at all — its subcommands only ever accept `${2:-}` as the package. For a targeted `-run` or verbose probe, use the direct `docker run ... go test -count=1 -v -run <pattern> ./internal/pkg/...` invocation documented above instead.

## Getting an authoritative test result while a teammate live-edits the SAME files mid-QA

Recurred 2026-08-05 on `fix/project-form-message-and-duplicates`: team-lead asked for a re-run after committing security fixes; mid-run, `go vet` in the primary worktree genuinely failed to compile (`sm.UpdateProject` arg-count mismatch against a signature another agent was actively changing) — by the time the run finished the tree had self-resolved past that AND grown further uncommitted changes. This is [[project_test_tooling]]'s existing "concurrency in the primary worktree" scenario recurring, with a concrete recipe that worked:

1. `git worktree add --detach <path> <commit-sha>` pinned to the last commit you actually want a verdict on (e.g. the SHA the teammate just told you they pushed/committed).
2. Run `vet`/`test`/`test-race` there via the direct `docker run` invocations (or `cd` in and use `./scripts/dev.sh ...` — see the race-image note above for why the latter is safer for `-race`).
3. `git worktree remove --force <path>` when done.

**Why:** A detached worktree is a separate checkout of one immutable commit — nothing another agent does to the primary worktree's files can touch it. This turns "the tree might be mid-edit when my run finishes" into a non-issue: the isolated result is correct for that SHA regardless of what happens elsewhere, and it's the honest answer to "does the branch as committed pass" even when "the branch as currently sitting on disk" is a moving target.
**How to apply:** Whenever a re-run is requested on a branch you know or suspect is being actively edited in the same worktree (teammate said "I just fixed X", or you already hit one live-edit race this session) — don't just re-run in place and hope it stays still. Pin to the SHA, isolate, report against that SHA explicitly, and separately flag (don't silently absorb) any uncommitted work you noticed but didn't evaluate — name the files and what changed, so the requester knows what's still unverified.

## The concurrent teammate can land a real COMMIT mid-QA, not just uncommitted edits

Observed 2026-08-05 (`feat/fold-duplicate-projects-on-a-host`, mutation-testing `MergeProjects`): mid-session, `git status` showed `HEAD` had moved — a new commit (`6d021b5`) had landed on the very branch under review, on top of which a teammate (apparently a code-review agent working `.claude/reviews/quil/*.md` findings) was live-editing the exact function (`sameAs`) I was mid-mutation on. The harness's own file-change system-reminder was the first signal, not `git status` — it fires the instant a tool sees the file differs from what it last wrote/read, before you'd think to check.

**How to apply:** Treat an unexpected file-change system-reminder on a file you are actively mutating as the same signal as a `git status` surprise — stop, diff against your last known state, and separate "their real feature content" from "my mutation" before touching anything, so a revert edit does not also strip their new field/logic. Then move immediately to the `git worktree add --detach <sha>` isolation recipe above — it works identically whether the concurrent change is committed or not, since you're pinning to a SHA either way. After isolating, a quick read-only `git diff` of the primary worktree (never edit it further) tells you whether the teammate's in-flight fix overlaps the gaps you're about to report — mention the overlap (or its absence) in the final report so the requester isn't told to fix something already being fixed.

## Mutation-testing a persistence round-trip: check what triggers the snapshot, not just what the snapshot contains

A round-trip test (`encode → handleMessage → snapshot → restore`) that calls the daemon's snapshot function **explicitly and directly** (e.g. `d.snapshot()`) right after `d.handleMessage(...)`, rather than relying on the handler's own persistence trigger (`d.requestSnapshot()`, debounced), verifies only that the snapshot WRITER correctly serializes the current in-memory state — it says nothing about whether the code path that fires in real usage actually schedules that write. Confirmed by mutation on `MsgMergeProjects` (`internal/daemon/daemon.go`): deleting the handler's own `d.requestSnapshot()` call left `TestMergeProjects_SurvivesTheWireAndARestart` fully green, because the test's own explicit `d.snapshot()` a few lines later papers over the missing trigger entirely.

**Why:** the test's stated purpose ("survives the wire and a restart") is not actually exercised for the "wire" half of persistence-scheduling — only for the "restart" half (does a snapshot, once taken, restore correctly). A developer who forgot the trigger call would ship a merge that is invisible on disk until the next unrelated snapshot or the 30s periodic tick — exactly the "half-persisted fold" failure mode the test's own doc comment worries about — and no test would fail.
**How to apply:** For any daemon round-trip test structured as `handleMessage(...)` followed by an explicit `d.snapshot()`/`sm.SnapshotState()` call, mutate away the handler's own `requestSnapshot()`/equivalent trigger line and re-run that exact test. If it still passes, the round trip is only testing serialization, not scheduling — call this out explicitly as a gap rather than crediting the test with covering "survives a restart" in the production sense.

**A concurrent agent can leave a scratch `zz_probe_test.go`-style file mid-session, targeting the SAME hazards you were asked to check, then delete it before you finish.** Observed 2026-08-07 on `fix/worktree-replace-and-branch-capture` (PR #136): an untracked `internal/tui/zz_probe_test.go` (4 `TestZZProbe_*` tests, not in the PR's file list) was present on first `dev.sh test` run, broke the whole-suite result with 4 genuine `FAIL`s, and had vanished (confirmed via `git status --short` and a fresh `ls`) by the time a follow-up command tried to reuse it minutes later — someone else's investigation, cleaned up after itself. Its probes were extremely well-targeted (broadcast-mid-replace leak, second-replace-same-tab overwrite, `renderPendingPane` narrow-rect overflow, ordinary-split-shows-worktree-text) and all four had already reproduced with concrete numbers in the captured output before it disappeared.
**How to apply:** An unfamiliar `Test<Something>Probe*`/`zz_*` file failing alongside your target package is a strong signal of exactly this, not a regression in the PR — cross-check `git status --short` (untracked) before treating it as real. Isolate your OWN pass/fail verdict from it via the detached-worktree recipe below (a fresh checkout never has untracked files). But don't discard its output: if you already captured a `FAIL` transcript before it vanished, that transcript is real evidence of a real bug — cite it as corroborating evidence for your own source-reading conclusion, note plainly that the file was untracked/out-of-scope and has since been removed, and independently confirm the underlying claim via your own mutation test where feasible rather than resting solely on a transcript you can no longer reproduce.

**Recurred 2026-08-06 on `feature/sidebar-and-worktree-panes` — this time on `createPaneAt`, not `MergeProjects`, confirming it's a pattern in this codebase rather than a one-off.** `createPaneAt` (`internal/daemon/daemon.go`) is the shared pane-construction function behind BOTH the ordinary `handleCreatePane` path and the new worktree-create path (`worktree_add.go`'s `createPaneInWorktree`), and it ends with `d.broadcastState(); d.requestSnapshot()`. Commenting out just the `d.requestSnapshot()` line and running the ENTIRE `internal/daemon` suite (`go test ./internal/daemon/...`, not a scoped subset) left it 100% green — including the PR's own new `TestSnapshot_WorktreeOwnershipSurvivesTheRoundTrip`, which (like the `MergeProjects` case) calls `d.snapshot()` directly on a hand-built pane rather than driving the real create path and relying on its trigger.
**How to apply:** This is now a STANDING check for any daemon PR that touches pane/tab creation, not just merge/fold code: grep the changed handler chain for its `d.requestSnapshot()` call, comment it out, and run the FULL `internal/daemon` suite (mutating a SHARED function like `createPaneAt` can only be validated suite-wide, since scoping to one new test file hides that the ordinary create path is equally uncovered). A clean run on that mutation is a genuine, reportable gap — the codebase has now shipped this exact blind spot twice.

## The same "set but never driven" gap shows up on TUI-side gate booleans/maps, not just daemon persistence triggers

Found 2026-08-06 QA'ing commit `0da6315` (`feature/sidebar-and-worktree-panes`, isolated worktree pinned to that SHA): `applyWorkspaceState`/`rebuildTabs` in `internal/tui/model.go` gained `if tab.Root != nil && !m.worktreeCreates[tab.ID] { tab.Root.PrunePlaceholders(); ... }` — an exemption that stops the routine placeholder-cleanup pass from ripping out a live placeholder while a worktree `git add` is still in flight (which takes seconds, unlike an ordinary create's microsecond window). Removing just the `&& !m.worktreeCreates[tab.ID]` clause and running the FULL `internal/tui` suite (`go test ./internal/tui/...`, not a scoped file) left it 100% green. Every test that touches `worktreeCreates` (`worktree_create_resp_test.go`) sets the map directly as test setup and asserts on `applyCreatePaneResp`/timeout unwinding — none of them drive `rebuildTabs`/`applyWorkspaceState` afterward with an unfilled placeholder still attached to the tab, so the exemption's actual effect (a broadcast landing mid-create does NOT prune the tab's live placeholder) is never exercised.

**Why this generalizes:** it's the same shape as the `d.requestSnapshot()` gap above, just on the client side — a boolean/map that GATES a cleanup/reconciliation step is well-tested for being SET (the arming side) and never tested for the thing it actually GATES (the suppression side). "The setter is covered" is not evidence "the gate works."
**How to apply:** For any PR adding a condition that suppresses an existing cleanup/reconciliation/prune step ("skip X while Y holds"), don't stop at confirming Y gets set/cleared correctly — grep for the READ site of the gate, comment out just that boolean/map-lookup clause (leave the rest of the surrounding logic intact), and run the full package suite fresh (`-count=1`). A clean run under that single-clause mutation is a real, reportable coverage gap in the PR under review, worth calling out explicitly even when every named new test independently passes its own mutation.

## A third variant: a test named after a SIDE EFFECT that only asserts the BOOKKEEPING around it

Found 2026-08-07, PR #136 (`fix/worktree-replace-and-branch-capture`): `TestReplace_WithoutAWorktreeStillDisposesImmediately` (`internal/tui/worktree_replace_test.go`) asserts `worktreeReplaced[tab.ID] == nil` and `worktreeCreates[tab.ID] == ""` — both bookkeeping maps — but never that `old.Dispose()` (which stops the pane's drain goroutine, per `pane_dispose_test.go`) actually ran. Deleting the `old.Dispose()` call in the `spec == nil` branch of `handleCreatePaneSplit` (`internal/tui/dialog.go`) and running the FULL `internal/tui` suite fresh left it 100% green — the goroutine leak this test's own name claims to guard against is invisible to it.
**Why this is a distinct variant from the gate-boolean case above:** there the map/flag itself IS the behavior under test (does the prune skip fire); here the map is a proxy the test checked instead of the actual resource-cleanup call the surrounding comment and test name are about. A green "bookkeeping cleared" assertion is not evidence the disposal happened — the two can and did diverge under mutation.
**How to apply:** When a test's NAME promises a resource-lifecycle effect (Dispose/Close/stop a goroutine/free a handle) but its assertions only touch a map or flag one step removed from that effect, mutate away the actual effect call (not the map write) and confirm the test still fails to fire — if it stays green, the test is checking the wrong thing and the real effect is uncovered.
