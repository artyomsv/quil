Found 2026-08-09 QA'ing PR #138 (`feat/keybinding-registry`, `internal/keymap` + `internal/tui/model.go`'s `handleKey`). Three concrete, mutation-confirmed gaps in a single dispatch-registry refactor — useful as a checklist for any future PR that resolves keys/commands/routes through a lookup table with more than one dispatch tier:

**1. A hand-checked (non-registry) key switch that lives OUTSIDE the thing under test has zero coverage by default.** `handleKey` resolves 38 actions through `m.keymap.MatchTier`, but three key groups (`f1`, `ctrl+n`, `alt+1..9`) are deliberately NOT registry actions — they're a bare `switch { case key == "..." }` after both tier lookups. Grepping every `_test.go` for the literal chords found NO test driving `ctrl+n` or `alt+1..9` through `handleKey`/`Update` at all. Mutating away each case arm one at a time and running the full package suite (`go test -count=1 ./internal/tui/...`) confirmed both: 100% green with zero dispatch. (F1 turned out to be accidentally covered — see #3.)
**How to apply:** When a PR adds a lookup-table dispatch mechanism, explicitly ask "what keys/commands are EXPLICITLY EXCLUDED from the table" (hardcoded, reserved, legacy) — those are the ones most likely to have never been tested, because they were never the "interesting" part of any prior refactor either. Mutate each one (delete the case arm, run the suite fresh) rather than assuming a static case-arm-presence test covers them — see #2.

**2. A test asserting "every action has a case arm" by `strings.Contains`-searching the function body is blind to WHICH switch the arm is in.** `TestHandleKey_EveryDispatchedActionHasACaseArm` (`internal/tui/keydispatch_test.go`) explicitly documents itself as "a STATIC check and says nothing about what a body does" — but even its author's framing undersells the gap: it also says nothing about *where* the arm lives. Physically moving one case arm (`project.new`, an early-tier action) from the early switch to the late switch — with the registry's `Action.Tier` field left untouched — left the ENTIRE `internal/tui` + `internal/keymap` suite green. `TestActions_TierSplitMatchesLegacySwitches` (keymap package) only checks the registry's `Tier` FIELD, not model.go's actual switch placement, so it can't see this either. The only test that would catch a *specific* early/late swap (`TestUpdate_RawKeysLoseToEarlyActionsAndBeatLateOnes`) is hardcoded to two actions (`pane.mute`, `pane.restart`) and doesn't generalize to the other ~37.
**How to apply:** For any refactor with N dispatch arms split across 2+ switches/tiers by a data field (Tier, priority, order…), don't trust a "does every ID appear as a case label somewhere" test to catch a misplaced arm. Physically relocate one arm across the seam (leaving the registry data unchanged) and run the full suite; if it stays green, say so explicitly as a gap — it generalizes to "any of the N arms could silently move and nothing would notice."

**3. A `Keys()`/`Display()`-style nil-safe registry reader with a hardcoded fallback can make an existing pre-refactor test stop meaning anything, without the test itself changing.** `reconnect.go`'s freeze-escape check was rewired from `isFreezeEscape(key, m.cfg.Keybindings.Quit)` to `isFreezeEscape(key, m.keymap.Keys("app.quit"))`. `reconnect_test.go` (untouched by this PR) never calls `m.initKeymap()`, so `m.keymap` is nil in every one of its tests; `Keymap.Keys` is nil-safe and returns `nil`, and `isFreezeEscape` falls back to a hardcoded `freezeEscapeKeys = ["ctrl+q", "ctrl+c"]` list — which happens to contain the SAME key (`ctrl+q`) the tests press. Pre-refactor, `m.cfg.Keybindings.Quit` was populated synchronously by `config.Default()` with no init step, so the same tests genuinely exercised the config-reading path; post-refactor they only prove the emergency fallback still works. Confirmed by mutating the action-ID string passed to `Keys()` to a typo (`"app.qut"`) — full suite stayed green, because every test either skips `initKeymap()` or uses the default binding that the fallback also covers.
**How to apply:** When a refactor moves a call site from "read a struct field directly" to "resolve through a registry/keymap that has a nil-safe fallback," check whether existing tests exercising that call site ever construct a REAL (non-nil) instance of the resolver, AND use a NON-default value that the fallback wouldn't also satisfy. If every existing test either skips initialization or uses a value indistinguishable from the fallback's own hardcoded set, the refactor has silently emptied a previously-meaningful test of its content — flag it even though the test file itself has zero diff.

General technique used for all three: pin a detached worktree to the PR's HEAD commit (see [[project_test_tooling]]'s isolation recipe), make the mutation, run the FULL affected package suite fresh (`-count=1`, no `dev.sh test` caching), confirm green, then immediately revert with `git checkout -- <file>` before the next mutation. One mutation at a time, not batched, or a compile error in one masks whether the other would have been caught.
